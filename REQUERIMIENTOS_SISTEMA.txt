================================================================================
1. DESCRIPCIÓN GENERAL DEL SISTEMA
================================================================================

Inventrix es un sistema web de gestión empresarial orientado a pequeñas y
medianas empresas, con enfoque especial en talleres de motos y negocios de
venta minorista en América Latina (Nicaragua). El sistema integra control de
inventario, gestión de ventas y compras, relaciones con clientes y
proveedores, un ciclo completo de órdenes de trabajo de taller con bitácora
fotográfica, cotizaciones y presupuestos, garantías, devoluciones, cuentas por
cobrar/pagar, caja y gastos operativos, reportes gerenciales (incluyendo
pronóstico de demanda asistido por IA) y una aplicación de escritorio
complementaria para el punto de venta.

Tecnologías principales:
  - Backend:  Django 6.x + Django REST Framework + PostgreSQL 16
  - Auth:     JWT (djangorestframework-simplejwt) con roles administrador/
              usuario, rotación de refresh tokens y throttling de login
  - Cifrado:  Fernet (paquete `cryptography`) para datos de contacto sensibles
              en reposo (teléfono/email de clientes y proveedores, claves de
              proveedores de IA)
  - Frontend: React 19 + Vite 7 + TailwindCSS 4 + React Query + Zustand +
              React Router
  - Storage:  Cloudflare R2 (compatible con S3) para imágenes de productos y
              bitácora de servicios
  - IA:       Integración opcional con OpenAI, Google Gemini, DeepSeek y
              Anthropic (Claude) para interpretar el pronóstico de demanda
  - App de escritorio: cliente nativo con verificación/descarga de
              actualizaciones intermediada por el backend (repo privado en
              GitHub)
  - Deploy:   Docker Compose (desarrollo/producción) / Vercel (frontend) /
              Gunicorn (backend)

RF-01: GESTIÓN DE PRODUCTOS
------------------------------------------------------------------------
RF-01.1  [ALTA]   El sistema debe permitir crear, editar, visualizar y eliminar
         productos.
RF-01.2  [ALTA]   Cada producto debe tener: SKU único, nombre, descripción,

         total, categoría, marca, proveedor, ubicación física e imagen.
RF-01.3  [ALTA]   El sistema debe generar alertas visuales cuando el stock de
         un producto caiga por debajo del stock mínimo definido.
RF-01.4  [ALTA]   El sistema debe permitir buscar productos por SKU, nombre u
         otros campos.
RF-01.5  [MEDIA]  El sistema debe permitir filtrar productos por categoría,
         marca, proveedor y estado de stock.
RF-01.6  [MEDIA]  El sistema debe calcular y mostrar el margen de ganancia de
         cada producto.
RF-01.7  [MEDIA]  El sistema debe permitir exportar el listado de productos en
         formato PDF y Excel.
RF-01.8  [ALTA]   El sistema debe registrar automáticamente todos los cambios
         realizados a un producto en un log de auditoría mediante triggers de
         base de datos.
RF-01.9  [MEDIA]  El sistema debe soportar carga y almacenamiento de imágenes
         de productos en Cloudflare R2.
RF-01.10 [ALTA]   El sistema debe exponer un filtro de productos con bajo stock
         en la API.
RF-01.11 [MEDIA]  El sistema debe permitir importar productos de forma masiva
         (por ejemplo, desde CSV).
RF-01.12 [MEDIA]  El sistema debe permitir generar e imprimir etiquetas con
         código de barras para los productos.

         ubicación física (bodega, pasillo, estante, gaveta).

RF-09: TALLER - ÓRDENES DE TRABAJO (SERVICIOS DE MOTO)
------------------------------------------------------------------------
RF-09.1  [ALTA]   El sistema debe gestionar el ciclo de vida completo de una
         orden de trabajo con los estados: Agendada, Recibida, En diagnóstico,
         En reparación, Esperando repuesto, Lista para entrega, Entregada y
         Cancelada.
RF-09.2  [ALTA]   El sistema debe validar las transiciones de estado
         permitidas y rechazar cambios de estado inválidos (por ejemplo, no
         se puede pasar de "Agendada" directo a "Entregada").
RF-09.3  [ALTA]   Cada orden de trabajo debe poder asociarse a un mecánico
         responsable.
RF-09.4  [ALTA]   El sistema debe permitir registrar los repuestos consumidos
         en una orden de trabajo, descontando automáticamente el stock del
         inventario.
RF-09.5  [ALTA]   El costo total de la orden de trabajo debe calcularse
         automáticamente como la suma de la mano de obra (precio congelado al
         agendar) más el valor de los repuestos consumidos.
RF-09.6  [MEDIA]  El sistema debe permitir agendar una cita (fecha y hora) para
         la orden de trabajo.
RF-09.7  [ALTA]   Al entregar una orden de trabajo, el sistema debe generar
         automáticamente la venta correspondiente (productos + mano de obra).
RF-09.8  [MEDIA]  Si la orden de trabajo tiene un presupuesto de reparación
         asociado, el sistema debe exigir que esté aprobado antes de permitir
         iniciar la reparación.
RF-09.9  [MEDIA]  El sistema debe generar un reporte de agenda del taller con
         la carga de trabajo por mecánico y la antigüedad de las órdenes por
         estado.
RF-09.10 [MEDIA]  El sistema debe generar un reporte de mantenimiento
         preventivo con las motos que ya deben revisarse según lo sugerido en
         su última entrega.

RF-10: BITÁCORA DE SERVICIOS (4 MÓDULOS)
------------------------------------------------------------------------
RF-10.1  [ALTA]   El sistema debe gestionar una bitácora de servicio con 4
         etapas: Recepción, Diagnóstico, Reparación y Entrega, vinculadas a
         los estados de la orden de trabajo.
RF-10.2  [ALTA]   Cada etapa debe permitir: notas detalladas, nombre del
         técnico responsable y carga de múltiples fotografías.
RF-10.3  [ALTA]   Las fotografías deben almacenarse en Cloudflare R2 y
         referenciarse mediante URLs en un array JSONB en la base de datos.
RF-10.4  [MEDIA]  La etapa de Recepción debe documentar: nivel de combustible
         y daños/rayones preexistentes.
RF-10.5  [MEDIA]  La etapa de Diagnóstico debe documentar: fallas encontradas
         con evidencia fotográfica.
RF-10.6  [ALTA]   La etapa de Reparación debe documentar: trabajo realizado,
         técnico responsable y fotos de progreso.
RF-10.7  [MEDIA]  La etapa de Entrega debe incluir: checklist de finalización
         y firma/confirmación de entrega al cliente.
RF-10.8  [MEDIA]  El sistema debe exponer una vista combinada de orden de
         trabajo + bitácora.

RF-11: COTIZACIONES Y PRESUPUESTOS
------------------------------------------------------------------------
RF-11.1  [ALTA]   El sistema debe permitir crear cotizaciones de dos tipos:
         proforma de productos (para clientes que solo compran mercadería) y
         presupuesto de reparación (ligado a una orden de trabajo del taller).
RF-11.2  [ALTA]   Cada cotización debe gestionar su estado: Pendiente,
         Aprobada, Rechazada o Convertida en venta.
RF-11.3  [ALTA]   El sistema debe calcular el total de la cotización como la
         suma de líneas de producto y líneas de mano de obra.
RF-11.4  [MEDIA]  El sistema debe calcular la fecha de vencimiento de la
         cotización a partir de su fecha de emisión y los días de validez
         configurados.
RF-11.5  [ALTA]   Al aprobar un presupuesto de reparación, el sistema debe
         cargar sus repuestos a la orden de trabajo y descontar el stock una
         única vez (protegido contra doble aprobación).
RF-11.6  [MEDIA]  El sistema debe permitir convertir una cotización aprobada en
         una orden de venta.
RF-11.7  [MEDIA]  El sistema debe permitir generar el documento de la
         cotización/presupuesto en PDF.

------------------------------------------------------------------------
RF-12: ÓRDENES DE COMPRA
------------------------------------------------------------------------
RF-12.1  [ALTA]   El sistema debe permitir crear órdenes de compra con
         múltiples productos, asociadas a un proveedor.
RF-12.2  [ALTA]   Cada orden debe gestionar su estado: Pendiente, Recibida o
         Cancelada.
RF-12.3  [ALTA]   Al marcar una orden como Recibida, el sistema debe
         incrementar automáticamente el stock de los productos involucrados,
         de forma idempotente (recibir dos veces no debe duplicar el stock).
RF-12.4  [ALTA]   El sistema debe calcular automáticamente subtotales,
         impuestos y totales de cada orden.
RF-12.5  [MEDIA]  El sistema debe permitir exportar órdenes de compra en PDF y
         Excel.
RF-12.6  [ALTA]   El sistema debe permitir agregar múltiples ítems (líneas de
         detalle) a cada orden, con cantidad y precio unitario por ítem.
RF-12.7  [ALTA]   El sistema debe registrar la fecha esperada y la fecha real
         de recepción de cada orden, para medir el desempeño del proveedor
         (velocidad y puntualidad de entrega).
RF-12.8  [ALTA]   El sistema debe gestionar cuentas por pagar por orden de
         compra: monto pagado, saldo pendiente y estado de pago (Pendiente,
         Pago Parcial, Pagado), permitiendo registrar pagos parciales (abonos)
         a proveedores.

------------------------------------------------------------------------
RF-13: ÓRDENES DE VENTA
------------------------------------------------------------------------
RF-13.1  [ALTA]   El sistema debe permitir crear órdenes de venta con múltiples
         productos y/o servicios de taller, asociadas a un cliente.
RF-13.2  [ALTA]   Al registrar una venta, el sistema debe decrementar
         automáticamente el stock de los productos vendidos.
RF-13.3  [ALTA]   El sistema debe calcular automáticamente subtotales y
         totales, soportando descuentos.
RF-13.4  [ALTA]   El sistema debe validar que la fecha de venta no sea una
         fecha futura.
RF-13.5  [MEDIA]  El sistema debe mantener el historial de ventas por cliente.
RF-13.6  [ALTA]   El sistema debe prevenir ventas cuando el stock disponible
         sea insuficiente para cubrir la cantidad solicitada.
RF-13.7  [ALTA]   El sistema debe permitir pagos por adelantado (abonos)
         sobre una venta, gestionando monto pagado, saldo pendiente y estado
         de pago (Pendiente, Pago Parcial, Pagado).
RF-13.8  [ALTA]   El sistema debe generar automáticamente una garantía por
         cada producto vendido que tenga garantía configurada.
RF-13.9  [MEDIA]  El sistema debe permitir generar e imprimir un recibo en PDF
         de la venta.
RF-13.10 [MEDIA]  El sistema debe generar un reporte de cuentas por cobrar,
         mostrando la antigüedad (aging) del saldo pendiente por cliente.

RF-14: DEVOLUCIONES DE CLIENTES
------------------------------------------------------------------------
RF-14.1  [ALTA]   El sistema debe permitir registrar devoluciones de mercadería
         vendida, asociadas a una venta y un cliente.
RF-14.2  [ALTA]   El importe de la devolución debe derivarse de las líneas
         reales de la venta, no de un monto ingresado libremente.
RF-14.3  [ALTA]   Una devolución procesada debe reingresar el stock devuelto

RF-14.4  [ALTA]   El saldo pendiente de cobro de la venta debe recalcularse
         restando el valor de las devoluciones procesadas.
RF-14.5  [MEDIA]  El sistema debe permitir anular una devolución, revirtiendo
         su efecto sobre el saldo.

------------------------------------------------------------------------

------------------------------------------------------------------------
RF-15.1  [ALTA]   El sistema debe permitir registrar devoluciones de mercadería
         a un proveedor, asociadas a una orden de compra recibida.
RF-15.2  [ALTA]   Una devolución a proveedor debe descontar el stock devuelto

RF-15.3  [ALTA]   El sistema debe permitir registrar si el proveedor reembolsó

RF-15.4  [ALTA]   El saldo pendiente de pago de la orden de compra debe
         recalcularse considerando lo devuelto y lo reembolsado.
RF-15.5  [MEDIA]  El sistema debe generar un reporte de devoluciones a

RF-16.2  [ALTA]   Cada garantía debe gestionar su estado: Activa, Vencida o

RF-16.3  [ALTA]   El sistema debe permitir registrar reclamaciones sobre una

RF-16.4  [ALTA]   Cada reclamación debe gestionar su estado: Pendiente, En

RF-17: MOVIMIENTOS DE INVENTARIO
------------------------------------------------------------------------
RF-17.1  [ALTA]   El sistema debe registrar automáticamente un movimiento de
         inventario ante cada cambio de stock: entrada, salida o ajuste.
RF-17.2  [ALTA]   Cada movimiento debe registrar: producto, tipo, cantidad,

         ajuste manual) y notas.
RF-17.3  [MEDIA]  El sistema debe permitir realizar ajustes manuales de
         inventario mediante un endpoint dedicado.
RF-17.4  [MEDIA]  El sistema debe permitir búsqueda y filtrado de movimientos
         por producto, tipo y rango de fecha.
RF-17.5  [ALTA]   El historial de movimientos debe ser de solo consulta (no
         editable una vez registrado).

RF-18: CAJA (SESIONES DE CAJA)
------------------------------------------------------------------------
RF-18.1  [ALTA]   El sistema debe permitir abrir una sesión de caja con un
         monto de apertura (fondo inicial), registrando el usuario que la
         abre.
RF-18.2  [ALTA]   El sistema debe garantizar que solo exista una sesión de
         caja abierta a la vez en todo el sistema.
RF-18.3  [ALTA]   El sistema debe permitir registrar movimientos manuales de
         efectivo (ingresos y retiros) dentro de una sesión abierta.
RF-18.4  [ALTA]   El sistema debe calcular el efectivo esperado en caja a
         partir del fondo inicial, los pagos en efectivo recibidos (ventas,
         abonos), los reembolsos de proveedores en efectivo, los ingresos y
         retiros manuales, los gastos operativos en efectivo y los pagos a
         proveedores en efectivo.
RF-18.5  [ALTA]   Al cerrar una sesión de caja, el sistema debe registrar el
         efectivo contado físicamente y calcular la diferencia (faltante o
         sobrante) contra el efectivo esperado.
RF-18.6  [ALTA]   Solo el usuario dueño de una sesión de caja abierta (o un
         administrador) puede cerrarla o registrar/consultar sus movimientos
         y su arqueo en vivo.
RF-18.7  [MEDIA]  Cualquier usuario autenticado debe poder consultar si hay una
         sesión de caja abierta y su titular, para saber si puede cobrar.
RF-18.8  [ALTA]   El listado histórico de sesiones de caja debe estar
         restringido a administradores.

RF-19: GASTOS OPERATIVOS

RF-19.2  [ALTA]   Cualquier usuario autenticado debe poder registrar un gasto

RF-19.3  [ALTA]   Un gasto en efectivo debe descontarse del efectivo esperado

RF-19.4  [MEDIA]  Consultar el listado completo, editar o eliminar gastos debe
         estar restringido a administradores.
RF-19.5  [MEDIA]  El sistema debe permitir filtrar gastos por categoría y rango
         de fechas.

RF-20: AUDITORÍA DE PRODUCTOS
------------------------------------------------------------------------
RF-20.1  [ALTA]   El sistema debe registrar automáticamente, mediante triggers
         de base de datos, cada modificación realizada a un producto.
RF-20.2  [ALTA]   Cada registro de auditoría debe capturar: campo modificado,
         valor anterior (JSON), valor nuevo (JSON), usuario responsable real

RF-20.3  [MEDIA]  El sistema debe exponer una página de "Logs de Auditoría"

         productos, de solo lectura.

RF-21: AUTENTICACIÓN Y GESTIÓN DE USUARIOS
------------------------------------------------------------------------
RF-21.1  [ALTA]   El sistema debe requerir autenticación (JWT) para acceder a
         prácticamente todos los endpoints de la API, con las únicas
         excepciones públicas de los endpoints de actualización de la app de
         escritorio.
RF-21.2  [ALTA]   El sistema debe emitir un token de acceso y uno de
         actualización (refresh) al iniciar sesión, con rotación y lista
         negra del refresh token al renovarlo o cerrar sesión.
RF-21.3  [ALTA]   El sistema debe soportar dos roles: Administrador (acceso
         total) y Usuario (operación del día a día: ventas, pagos, POS,
         cotizaciones, devoluciones, alta de clientes/proveedores), sin
         permiso para acciones destructivas sobre catálogo/inventario
         (eliminar productos/clientes/proveedores, importar productos, ajustar
         stock, gestionar órdenes de compra).
RF-21.4  [ALTA]   El intento de inicio de sesión debe estar limitado en tasa
         (rate limiting) para mitigar ataques de fuerza bruta.
RF-21.5  [MEDIA]  El sistema debe exponer el perfil del usuario autenticado
         (nombre de usuario, email, rol) y permitir cerrar sesión invalidando
         el token en el servidor.
RF-21.6  [MEDIA]  El sistema debe permitir a un administrador crear, editar y
         desactivar usuarios del sistema.

------------------------------------------------------------------------
RF-22: PUNTO DE VENTA (POS)
------------------------------------------------------------------------
RF-22.1  [ALTA]   El sistema debe ofrecer una pantalla de punto de venta
         optimizada para registrar ventas rápidamente.
RF-22.2  [MEDIA]  El POS debe permitir escanear códigos de barras de productos
         mediante la cámara del dispositivo para agregarlos a la venta.
RF-22.3  [MEDIA]  El POS debe reflejar en tiempo real si hay una sesión de

RF-23.2  [MEDIA]  El pronóstico debe usar el plazo de entrega medido de cada

RF-23.3  [BAJA]   El sistema debe permitir interpretar el pronóstico de

RF-23.4  [MEDIA]  El sistema debe permitir configurar, por proveedor de IA

RF-23.5  [ALTA]   Solo un proveedor de IA puede estar activo a la vez.
RF-23.6  [ALTA]   La clave de API de cada proveedor de IA debe almacenarse

         únicamente una versión enmascarada.
RF-23.7  [ALTA]   La configuración de proveedores de IA debe estar restringida

RF-24: RESPALDOS DE BASE DE DATOS

RF-24.3  [MEDIA]  El sistema debe soportar además un respaldo automatizado

RF-24.4  [ALTA]   La descarga de respaldos debe estar restringida a

RF-25: ACTUALIZACIONES DE LA APLICACIÓN DE ESCRITORIO

RF-25.2  [MEDIA]  El sistema debe exponer un endpoint público que redirija a

RF-25.4  [MEDIA]  Ambos endpoints deben tener limitación de tasa (rate

RF-26.5  [ALTA]   El sistema debe generar un reporte de cuentas por cobrar

3. REQUERIMIENTOS NO FUNCIONALES
================================================================================

------------------------------------------------------------------------
RNF-01: RENDIMIENTO
------------------------------------------------------------------------
RNF-01.1 [ALTA]   El tiempo de respuesta de la API para operaciones CRUD
         estándar no debe superar los 500 ms bajo carga normal.
RNF-01.2 [ALTA]   El frontend debe implementar code splitting y lazy loading
         para que el tiempo de carga inicial no supere los 3 segundos en
         conexión estándar.
RNF-01.3 [MEDIA]  Las consultas de reportes con grandes volúmenes de datos
         deben completarse en menos de 5 segundos.
RNF-01.4 [MEDIA]  Se debe implementar debounce en la búsqueda global para
         evitar solicitudes innecesarias al servidor.
RNF-01.5 [MEDIA]  El sistema debe usar React Query para cachear respuestas del
         servidor y reducir llamadas redundantes a la API.
RNF-01.6 [BAJA]   Las imágenes subidas deben optimizarse antes del
         almacenamiento y servirse desde CDN (Cloudflare R2).
RNF-01.7 [MEDIA]  Los reportes financieros en vivo (cuentas por cobrar/pagar)
         no deben cachearse; el resto de reportes puede cachearse brevemente
         para reducir carga en la base de datos.

------------------------------------------------------------------------
RNF-02: SEGURIDAD
------------------------------------------------------------------------
RNF-02.1 [ALTA]   Todos los secretos del sistema (claves de base de datos,
         credenciales de R2, SECRET_KEY, clave de cifrado, token de GitHub)
         deben gestionarse mediante variables de entorno y no deben estar en
         el código fuente.
RNF-02.2 [ALTA]   El sistema debe configurar CORS restringido a los dominios
         autorizados en producción, sin permitir credenciales cross-origin
         (la autenticación viaja por header Authorization, no por cookies).
RNF-02.3 [ALTA]   Todos los datos de entrada del usuario deben ser validados y
         sanitizados mediante los serializers de Django REST Framework para
         prevenir inyección SQL y otros ataques.
RNF-02.4 [ALTA]   El modo DEBUG de Django debe estar deshabilitado en
         producción.
RNF-02.5 [ALTA]   Las contraseñas, tokens y datos sensibles nunca deben
         loguearse ni exponerse en respuestas de la API.
RNF-02.6 [ALTA]   El sistema debe proteger contra XSS mediante el manejo seguro
         de contenido dinámico en React.
RNF-02.7 [ALTA]   Prácticamente todos los endpoints de la API deben requerir
         autenticación JWT; las únicas excepciones públicas deben limitarse a
         endpoints que no reciben datos de entrada ni tocan la base de datos
         (verificación/descarga de la app de escritorio).
RNF-02.8 [ALTA]   El sistema debe implementar segregación de funciones por rol
         (administrador/usuario) en las operaciones de escritura, incluyendo
         reglas de propiedad (por ejemplo, un operador solo puede cerrar u
         operar su propia sesión de caja).
RNF-02.9 [ALTA]   El sistema debe limitar la tasa de peticiones (throttling)
         de forma diferenciada: anónimas, autenticadas, login (anti fuerza
         bruta) y verificación de actualizaciones de escritorio; debe
         calcular el cliente real detrás de un proxy inverso de forma
         confiable (no basarse en cabeceras que el cliente pueda falsificar).
RNF-02.10 [ALTA]  Los datos de contacto sensibles (teléfono y email de
         clientes y proveedores) y las claves de proveedores de IA deben
         cifrarse en reposo mediante un mecanismo simétrico auditado (Fernet),
         con la clave de cifrado gestionada fuera del código fuente.
RNF-02.11 [ALTA]  Los tokens JWT emitidos deben tener vida corta (access
         token), soportar renovación transparente (refresh con rotación) e
         invalidarse (lista negra) al cerrar sesión o rotar.
RNF-02.12 [ALTA]  Los respaldos de base de datos exportables deben excluir
         credenciales de sesión y claves de proveedores de IA, y su descarga
         debe restringirse a administradores.
RNF-02.13 [MEDIA] En producción, el sistema debe habilitar cabeceras de
         seguridad HTTP adicionales (HSTS, X-Content-Type-Options) y operar
         detrás de HTTPS terminado por el proxy inverso.

------------------------------------------------------------------------
RNF-03: DISPONIBILIDAD Y CONFIABILIDAD
------------------------------------------------------------------------
RNF-03.1 [ALTA]   El sistema debe garantizar consistencia transaccional: las
         operaciones que afectan múltiples tablas (p. ej., recibir una orden
         actualiza stock y crea movimiento; cerrar caja congela el arqueo) se
         deben ejecutar dentro de una transacción atómica, con bloqueo cuando
         corresponda para evitar condiciones de carrera (p. ej., abrir dos
         cajas simultáneamente).
RNF-03.2 [ALTA]   Las operaciones de eliminación deben gestionar correctamente
         las restricciones de clave foránea y notificar al usuario cuando no
         sea posible eliminar un registro con dependencias activas.
RNF-03.3 [ALTA]   El sistema debe implementar manejo centralizado de errores
         mediante middleware en el backend y manejo de excepciones en el
         frontend.
RNF-03.4 [MEDIA]  El sistema debe mostrar notificaciones toast al usuario ante
         éxitos y errores en operaciones críticas.
RNF-03.5 [ALTA]   Las operaciones que descuentan o reingresan stock, y las que
         actualizan saldos financieros (ventas, compras, devoluciones, pagos),
         deben ser idempotentes ante reintentos (no deben poder aplicarse dos
         veces por error).
RNF-03.6 [MEDIA]  Los endpoints públicos (actualizaciones de escritorio) deben
         cachear la dependencia externa (GitHub) para no degradar la
         disponibilidad del resto de la API ante fallas o lentitud de
         terceros.

------------------------------------------------------------------------
RNF-04: ESCALABILIDAD
------------------------------------------------------------------------
RNF-04.1 [MEDIA]  La arquitectura debe soportar la adición de nuevos módulos
         sin refactorización mayor de los existentes.
RNF-04.2 [MEDIA]  El backend debe estar preparado para escalar horizontalmente
         mediante el uso de Gunicorn con múltiples workers.
RNF-04.3 [ALTA]   El sistema de almacenamiento de imágenes debe ser
         independiente del servidor de aplicación, utilizando Cloudflare R2.
RNF-04.4 [ALTA]   La base de datos debe ser PostgreSQL en producción para
         soportar funcionalidades avanzadas (JSONB, triggers, índices
         compuestos, constraints condicionales).
RNF-04.5 [MEDIA]  El catálogo de proveedores de IA debe poder ampliarse
         agregando una entrada de configuración, sin cambios al modelo de
         datos ni a las migraciones.

------------------------------------------------------------------------
RNF-05: MANTENIBILIDAD
------------------------------------------------------------------------
RNF-05.1 [ALTA]   El backend debe seguir el patrón de capas: Views →
         Serializers → Services/Utils → Models, separando responsabilidades
         claramente.
RNF-05.2 [ALTA]   El frontend debe organizar el código en: pages, components
         (ui / forms / domain / layout / auth), hooks, services y utils.
RNF-05.3 [MEDIA]  Los hooks de React deben encapsular la lógica de estado y
         llamadas a la API, evitando código duplicado entre páginas.
RNF-05.4 [ALTA]   El sistema de base de datos debe versionarse mediante

RNF-05.5 [MEDIA]  Los cambios en la base de datos (triggers de auditoría,

RNF-05.6 [MEDIA]  Las decisiones de diseño no evidentes (por qué un campo se
         cifra o no, por qué un endpoint es público, por qué se congela un

         expliquen el motivo, no el qué.

RNF-06: USABILIDAD
------------------------------------------------------------------------
RNF-06.1 [ALTA]   La interfaz debe ser completamente responsiva y funcional en
         dispositivos móviles, tablets y escritorio (diseño mobile-first).
RNF-06.2 [MEDIA]  El sistema debe ofrecer un modo oscuro completo (dark mode)

RNF-06.4 [ALTA]   Los formularios deben implementar validación en tiempo real

RNF-06.5 [ALTA]   Los diálogos de confirmación deben presentarse antes de

RNF-06.6 [MEDIA]  El sistema debe mostrar indicadores de estado visual para

RNF-06.7 [MEDIA]  La navegación debe ser intuitiva, con el inicio organizado

RNF-07: COMPATIBILIDAD
------------------------------------------------------------------------
RNF-07.1 [ALTA]   El frontend debe ser compatible con las versiones actuales

RNF-07.2 [MEDIA]  La API REST debe seguir las convenciones estándar HTTP

RNF-07.3 [BAJA]   El sistema de almacenamiento de archivos debe ser compatible

RNF-07.4 [ALTA]   El sistema debe funcionar correctamente en entornos de

RNF-08: PORTABILIDAD Y DESPLIEGUE

RNF-08.2 [MEDIA]  El frontend debe poder desplegarse en Vercel con

RNF-08.4 [MEDIA]  La colección de archivos estáticos de Django debe ejecutarse

RNF-08.5 [ALTA]   Las migraciones de base de datos deben poder ejecutarse de

RNF-08.6 [MEDIA]  El entorno de desarrollo local no requiere Docker: el

RNF-09: VALIDACIÓN DE DATOS

RNF-12.5 [MEDIA]  Cada movimiento de efectivo dentro de una sesión de caja

================================================================================
4. RESTRICCIONES TÉCNICAS
================================================================================

RT-01  [ALTA]   Se requiere PostgreSQL 16+ en producción. No se soporta SQLite
       en producción debido al uso de JSONB, triggers, constraints
       condicionales y funciones específicas de PostgreSQL.

RT-02  [ALTA]   El almacenamiento de imágenes requiere acceso a Cloudflare R2
       o un servicio compatible con la API de Amazon S3 (bucket_name,
       access_key, secret_key, endpoint_url).

RT-03  [ALTA]   El backend requiere Python 3.12 o superior.

RT-04  [ALTA]   El frontend requiere Node.js 18+ para construcción con Vite 7.

RT-05  [ALTA]   El despliegue en producción requiere HTTPS para garantizar la
       seguridad de los datos en tránsito.

RT-06  [ALTA]   Las migraciones de base de datos deben ejecutarse en orden
       estricto para mantener la integridad referencial del esquema.

RT-07  [ALTA]   En producción son obligatorias las variables de entorno
       SECRET_KEY y FIELD_ENCRYPTION_KEY; el arranque debe fallar de forma
       explícita si faltan, en vez de operar sin cifrado.

RT-08  [MEDIA]  El uso de IA para el pronóstico de demanda requiere una clave
       de API válida de al menos uno de los proveedores soportados (OpenAI,
       Google Gemini, DeepSeek, Anthropic); sin ella, el pronóstico numérico
       sigue funcionando sin la interpretación en lenguaje natural.

RT-09  [MEDIA]  Las actualizaciones de la app de escritorio requieren un token
       de GitHub con acceso de lectura al repositorio privado del instalador
       (GITHUB_DESKTOP_TOKEN, GITHUB_DESKTOP_REPO).

RT-10  [ALTA]   El sistema debe operar detrás de exactamente el número de
       proxies de confianza configurado (NUM_PROXIES), para que el
       limitador de tasa identifique correctamente al cliente real.

5. ENTIDADES Y RELACIONES PRINCIPALES
================================================================================

  Producto           --> Categoria (N:1)
  Producto           --> Marca (N:1)
  Producto           --> Proveedor (N:1, opcional)
  Producto           --> Ubicacion (N:1, opcional)
  Proveedor          --> OrdenCompra (1:N)
  OrdenCompra        --> DetalleOrdenCompra (1:N) --> Producto (N:1)
  OrdenCompra        --> PagoCompra (1:N)
  OrdenCompra        --> DevolucionCompra (1:N) --> ProductoDevolucionCompra (1:N)
  Cliente            --> OrdenVenta (1:N)
  OrdenVenta         --> DetalleOrdenVenta (1:N) --> Producto (N:1)
  OrdenVenta         --> PagoVenta (1:N)
  OrdenVenta         --> Devolucion (1:N)
  OrdenVenta         --> Garantia (1:N) --> ReclamacionGarantia (1:N)
  Cliente            --> Moto (1:N)
  Moto               --> ServicioMoto (1:N)
  ServicioMoto       --> BitacoraServicio (1:N, una por módulo)
  ServicioMoto       --> ServicioRepuesto (1:N) --> Producto (N:1)
  ServicioMoto       --> Cotizacion (1:N, tipo=reparacion)
  ServicioMoto       --> OrdenVenta (N:1, al entregar)
  Cotizacion         --> ServicioCotizacion (1:N) --> Servicio (N:1)
  Cliente            --> Cotizacion (1:N)
  Usuario            --> SesionCaja (1:N)
  SesionCaja         --> MovimientoCaja (1:N)
  SesionCaja         --> PagoVenta / PagoCompra / Gasto / DevolucionCompra (1:N)
  CategoriaGasto     --> Gasto (1:N)
  Producto           --> MovimientoInventario (1:N)
  Producto           --> AuditoriaProducto (1:N) [via trigger]

7. HISTORIAS DE USUARIO DE ALTO NIVEL
================================================================================

HU-01  Como administrador, quiero ver el estado del inventario en tiempo real
       para tomar decisiones de reabastecimiento oportunas.

HU-02  Como vendedor, quiero registrar una venta rápidamente desde el punto de
       venta, escaneando el código de barras del producto, para que el stock
       se actualice automáticamente.

HU-03  Como comprador, quiero crear una orden de compra a un proveedor y
       registrar su recepción para actualizar el inventario sin errores
       manuales, y llevar el saldo que le debo.

HU-04  Como mecánico, quiero documentar cada etapa de una orden de trabajo con
       fotos y notas, y registrar los repuestos que consumo, para mantener un
       registro profesional y que el costo se calcule solo.

HU-05  Como gerente, quiero generar reportes de ventas, rentabilidad y estado
       de resultados por período en Excel o PDF para presentar resultados a la
       dirección.

HU-06  Como auditor, quiero ver el historial completo de cambios en el
       inventario con usuario y fecha para garantizar la trazabilidad de los
       datos.

HU-07  Como usuario, quiero buscar cualquier producto, cliente o proveedor
       desde cualquier pantalla con un atajo de teclado para trabajar más
       rápido.

HU-08  Como cajero, quiero abrir mi turno de caja con un fondo inicial y
       cerrarlo cuadrando el efectivo contado contra lo que el sistema
       calculó, para detectar faltantes o sobrantes al momento.

HU-09  Como cliente del taller, quiero recibir un presupuesto de reparación
       antes de que empiecen a trabajar en mi moto, para aprobarlo o
       rechazarlo con el costo por delante.

HU-10  Como administrador, quiero configurar un proveedor de IA para que el
       pronóstico de demanda me explique en lenguaje simple qué me conviene
       comprar, sin que mi clave de API quede expuesta.

HU-11  Como dueño del negocio sin equipo de IT, quiero descargar un respaldo
       completo de mis datos con un clic, para tener mi propia copia de
       seguridad.

HU-12  Como técnico en el taller, quiero usar la app de escritorio y que me
       avise sola cuando haya una versión nueva, sin tener que ir a buscarla.
