================================================================================
1. DESCRIPCIÓN GENERAL DEL SISTEMA
================================================================================

Inventrix es un sistema web de gestión empresarial orientado a pequeñas y
medianas empresas, con enfoque especial en talleres de motos y negocios de
venta minorista en América Latina (Nicaragua). El sistema integra control de
inventario, gestión de ventas y compras, relaciones con clientes y proveedores,
y un sistema especializado de bitácora de servicios para motos con soporte
fotográfico en la nube.

Tecnologías principales:
  - Backend:  Django 6.0 + Django REST Framework + PostgreSQL 16
  - Frontend: React 19 + Vite 7 + TailwindCSS 4 + React Query + Zustand
  - Storage:  Cloudflare R2 (compatible con S3) para almacenamiento de imágenes
  - Deploy:   Docker / Vercel (frontend) / Gunicorn (backend)

------------------------------------------------------------------------
RF-01.1  [ALTA]   El sistema debe permitir crear, editar, visualizar y eliminar

RF-01.3  [ALTA]   El sistema debe generar alertas visuales cuando el stock de

RF-01.4  [ALTA]   El sistema debe permitir buscar productos por SKU, nombre u
         otros campos.
RF-01.5  [MEDIA]  El sistema debe permitir filtrar productos por categoría,
         marca, proveedor y estado de stock.
RF-01.6  [MEDIA]  El sistema debe calcular y mostrar el margen de ganancia de
         cada producto.
RF-01.7  [MEDIA]  El sistema debe permitir exportar el listado de productos en
         formato PDF y Excel.
RF-01.8  [ALTA]   El sistema debe registrar automáticamente todos los cambios
         realizados a un producto en un log de auditoría mediante triggers de
         base de datos.
RF-01.9  [MEDIA]  El sistema debe soportar carga y almacenamiento de imágenes
         de productos en Cloudflare R2.
RF-01.10 [ALTA]   El sistema debe exponer un filtro de productos con bajo stock
         en la API.

RF-02.2  [ALTA]   Cada producto debe poder pertenecer a una categoría.

         disponibles.

------------------------------------------------------------------------

RF-04.2  [ALTA]   Cada proveedor debe tener: nombre de empresa, persona de

RF-09.1  [ALTA]   El sistema debe gestionar una bitácora de servicio con 4

RF-09.2  [ALTA]   Cada etapa debe permitir: notas detalladas, nombre del

RF-09.4  [MEDIA]  La etapa de Recepción debe documentar: estado inicial, nivel

RF-09.5  [MEDIA]  La etapa de Diagnóstico debe documentar: problemas
         identificados con evidencia fotográfica.
RF-09.6  [ALTA]   La etapa de Reparación debe documentar: trabajos realizados,
         técnico responsable y fotos de progreso.
RF-09.7  [MEDIA]  La etapa de Entrega debe incluir: checklist de finalización
         y confirmación de entrega al cliente.
RF-09.8  [MEDIA]  El sistema debe exponer una vista combinada de servicio +
         bitácora.

RF-10: ÓRDENES DE COMPRA
------------------------------------------------------------------------
RF-10.1  [ALTA]   El sistema debe permitir crear órdenes de compra con
         múltiples productos, asociadas a un proveedor.
RF-10.2  [ALTA]   Cada orden debe gestionar su estado: Pendiente, Recibida o
         Cancelada.
RF-10.3  [ALTA]   Al marcar una orden como Recibida, el sistema debe incrementar
         automáticamente el stock de los productos involucrados.
RF-10.4  [ALTA]   El sistema debe calcular automáticamente subtotales, impuestos
         y totales de cada orden.
RF-10.5  [MEDIA]  El sistema debe permitir exportar órdenes de compra en PDF y
         Excel.
RF-10.6  [ALTA]   El sistema debe permitir agregar múltiples ítems (líneas de

RF-11: ÓRDENES DE VENTA
------------------------------------------------------------------------
RF-11.1  [ALTA]   El sistema debe permitir crear órdenes de venta con múltiples
         productos, asociadas a un cliente.
RF-11.2  [ALTA]   Al registrar una venta, el sistema debe decrementar
         automáticamente el stock de los productos vendidos.
RF-11.3  [ALTA]   El sistema debe calcular automáticamente subtotales y totales,
         soportando descuentos.
RF-11.4  [ALTA]   El sistema debe validar que la fecha de venta no sea una
         fecha futura.
RF-11.5  [MEDIA]  El sistema debe mantener el historial de ventas por cliente.
RF-11.6  [ALTA]   El sistema debe prevenir ventas cuando el stock disponible sea

------------------------------------------------------------------------
RF-12: MOVIMIENTOS DE INVENTARIO

RF-12.2  [ALTA]   Cada movimiento debe registrar: producto, tipo, cantidad,

RF-12.3  [MEDIA]  El sistema debe permitir realizar ajustes manuales de

RF-12.4  [MEDIA]  El sistema debe permitir búsqueda y filtrado de movimientos

RF-12.5  [ALTA]   El historial de movimientos debe ser de solo consulta (no

------------------------------------------------------------------------

------------------------------------------------------------------------
RF-13.1  [ALTA]   El sistema debe generar un reporte de inventario con: estado

RF-13.2  [ALTA]   El sistema debe generar un reporte de ventas filtrable por

RF-13.3  [ALTA]   El sistema debe generar un reporte de compras filtrable por

RF-13.6  [MEDIA]  El sistema debe permitir exportar todos los reportes en PDF y

RF-14.1  [ALTA]   El sistema debe registrar automáticamente, mediante triggers

================================================================================
3. REQUERIMIENTOS NO FUNCIONALES
================================================================================

------------------------------------------------------------------------
RNF-01: RENDIMIENTO
------------------------------------------------------------------------
RNF-01.1 [ALTA]   El tiempo de respuesta de la API para operaciones CRUD
         estándar no debe superar los 500 ms bajo carga normal.
RNF-01.2 [ALTA]   El frontend debe implementar code splitting y lazy loading
         para que el tiempo de carga inicial no supere los 3 segundos en
         conexión estándar.
RNF-01.3 [MEDIA]  Las consultas de reportes con grandes volúmenes de datos
         deben completarse en menos de 5 segundos.
RNF-01.4 [MEDIA]  Se debe implementar debounce en la búsqueda global para
         evitar solicitudes innecesarias al servidor.
RNF-01.5 [MEDIA]  El sistema debe usar React Query para cachear respuestas del
         servidor y reducir llamadas redundantes a la API.
RNF-01.6 [BAJA]   Las imágenes subidas deben optimizarse antes del
         almacenamiento y servirse desde CDN (Cloudflare R2).

------------------------------------------------------------------------
RNF-02: SEGURIDAD
------------------------------------------------------------------------
RNF-02.1 [ALTA]   Todos los secretos del sistema (claves de base de datos,
         credenciales de R2, tokens) deben gestionarse mediante variables de
         entorno y no deben estar en el código fuente.
RNF-02.2 [ALTA]   El sistema debe configurar CORS restringido a los dominios
         autorizados en producción.
RNF-02.3 [ALTA]   Todos los datos de entrada del usuario deben ser validados y
         sanitizados mediante los serializers de Django REST Framework para
         prevenir inyección SQL y otros ataques.
RNF-02.4 [ALTA]   El modo DEBUG de Django debe estar deshabilitado en producción.
RNF-02.5 [ALTA]   Las contraseñas y datos sensibles nunca deben loguearse ni
         exponerse en respuestas de la API.
RNF-02.6 [ALTA]   El sistema debe proteger contra XSS mediante el manejo seguro
         de contenido dinámico en React.
RNF-02.7 [MEDIA]  Los endpoints de la API deben requerir autenticación para
         operaciones de escritura (cuando se implemente autenticación).

------------------------------------------------------------------------
RNF-03: DISPONIBILIDAD Y CONFIABILIDAD
------------------------------------------------------------------------
RNF-03.1 [ALTA]   El sistema debe garantizar consistencia transaccional: las
         operaciones que afectan múltiples tablas (e.g., recibir una orden
         actualiza stock y crea movimiento) deben ejecutarse dentro de una
         transacción atómica.
RNF-03.2 [ALTA]   Las operaciones de eliminación deben gestionar correctamente
         las restricciones de clave foránea y notificar al usuario cuando no
         sea posible eliminar un registro con dependencias activas.
RNF-03.3 [ALTA]   El sistema debe implementar manejo centralizado de errores
         mediante middleware en el backend y manejo de excepciones en el
         frontend.
RNF-03.4 [MEDIA]  El sistema debe mostrar notificaciones toast al usuario ante
         éxitos y errores en operaciones críticas.

------------------------------------------------------------------------
RNF-04: ESCALABILIDAD
------------------------------------------------------------------------
RNF-04.1 [MEDIA]  La arquitectura debe soportar la adición de nuevos módulos
         sin refactorización mayor de los existentes.
RNF-04.2 [MEDIA]  El backend debe estar preparado para escalar horizontalmente
         mediante el uso de Gunicorn con múltiples workers.
RNF-04.3 [ALTA]   El sistema de almacenamiento de imágenes debe ser independiente
         del servidor de aplicación, utilizando Cloudflare R2.
RNF-04.4 [ALTA]   La base de datos debe ser PostgreSQL en producción para
         soportar funcionalidades avanzadas (JSONB, triggers, índices
         compuestos).

------------------------------------------------------------------------
RNF-05: MANTENIBILIDAD
------------------------------------------------------------------------
RNF-05.1 [ALTA]   El backend debe seguir el patrón de capas: Views →
         Serializers → Services → Models, separando responsabilidades
         claramente.
RNF-05.2 [ALTA]   El frontend debe organizar el código en: pages, components
         (ui / forms / domain), hooks, services y utils.
RNF-05.3 [MEDIA]  Los hooks de React deben encapsular la lógica de estado y
         llamadas a la API, evitando código duplicado entre páginas.
RNF-05.4 [ALTA]   El sistema de base de datos debe versionarse mediante
         migraciones de Django para garantizar reproducibilidad del esquema.
RNF-05.5 [MEDIA]  Los cambios en la base de datos (triggers de auditoría,
         scripts SQL) deben documentarse y versionarse junto con el código.

------------------------------------------------------------------------
RNF-06: USABILIDAD
------------------------------------------------------------------------
RNF-06.1 [ALTA]   La interfaz debe ser completamente responsiva y funcional en
         dispositivos móviles, tablets y escritorio (diseño mobile-first).
RNF-06.2 [MEDIA]  El sistema debe ofrecer un modo oscuro completo (dark mode)
         que persista la preferencia del usuario.
RNF-06.3 [MEDIA]  El sistema debe proporcionar feedback visual inmediato
         mediante skeleton loaders durante la carga de datos y animaciones de
         transición entre vistas.
RNF-06.4 [ALTA]   Los formularios deben implementar validación en tiempo real
         con mensajes de error claros y específicos por campo.
RNF-06.5 [ALTA]   Los diálogos de confirmación deben presentarse antes de
         ejecutar operaciones destructivas (eliminaciones).
RNF-06.6 [MEDIA]  El sistema debe mostrar indicadores de estado visual para
         registros con datos críticos (e.g., productos con bajo stock
         resaltados).
RNF-06.7 [MEDIA]  La navegación debe ser intuitiva con accesos directos desde
         el dashboard a las secciones más utilizadas.

------------------------------------------------------------------------
RNF-07: COMPATIBILIDAD
------------------------------------------------------------------------
RNF-07.1 [ALTA]   El frontend debe ser compatible con las versiones actuales
         de los principales navegadores web: Chrome, Firefox, Safari y Edge.
RNF-07.2 [MEDIA]  La API REST debe seguir las convenciones estándar HTTP
         (códigos de estado, verbos, headers) para facilitar integraciones
         futuras.
RNF-07.3 [BAJA]   El sistema de almacenamiento de archivos debe ser compatible
         con la API S3 para facilitar la migración a otros proveedores cloud.
RNF-07.4 [ALTA]   El sistema debe funcionar correctamente en entornos de
         desarrollo (Docker Compose), staging y producción sin cambios de
         código, solo mediante variables de entorno.

------------------------------------------------------------------------
RNF-08: PORTABILIDAD Y DESPLIEGUE
------------------------------------------------------------------------
RNF-08.1 [ALTA]   El sistema debe poder desplegarse completamente mediante
         Docker Compose con un solo comando en desarrollo.
RNF-08.2 [MEDIA]  El frontend debe poder desplegarse en Vercel con
         configuración mínima (vercel.json incluido).
RNF-08.3 [ALTA]   El backend debe servirse mediante Gunicorn como servidor
         WSGI en producción.
RNF-08.4 [MEDIA]  La colección de archivos estáticos de Django debe ejecutarse
         automáticamente en el proceso de despliegue.
RNF-08.5 [ALTA]   Las migraciones de base de datos deben poder ejecutarse de
         forma automatizada como parte del proceso de despliegue.

------------------------------------------------------------------------
RNF-09: VALIDACIÓN DE DATOS
------------------------------------------------------------------------
RNF-09.1 [ALTA]   El sistema debe aplicar validación en tres capas: HTML5
         nativo en el navegador, JavaScript en el frontend (onChange y
         onSubmit) y validación de negocio en los serializers del backend.
RNF-09.2 [ALTA]   El sistema debe impedir el registro de órdenes de venta con
         fecha futura mediante validación en frontend y backend.
RNF-09.3 [ALTA]   Los rangos de fechas en reportes deben validarse: fecha
         inicio ≤ fecha fin, y ambas fechas ≤ fecha actual.
RNF-09.4 [ALTA]   El sistema debe validar que el stock no quede negativo al
         procesar una venta o ajuste de inventario.
RNF-09.5 [ALTA]   Los campos únicos (SKU, códigos) deben validarse contra
         duplicados antes de confirmar la creación o edición.

------------------------------------------------------------------------
RNF-10: EXPORTACIÓN Y FORMATOS
------------------------------------------------------------------------
RNF-10.1 [MEDIA]  Las exportaciones a PDF deben usar jsPDF con formato
         profesional, incluyendo encabezados, paginación y logotipo cuando
         corresponda.
RNF-10.2 [MEDIA]  Las exportaciones a Excel deben usar ExcelJS para generar
         archivos .xlsx con formato estructurado y columnas correctamente
         tipadas.
RNF-10.3 [MEDIA]  Las exportaciones deben incluir los mismos filtros aplicados
         en la vista actual del listado.

------------------------------------------------------------------------
RNF-11: INTERNACIONALIZACIÓN Y LOCALIZACIÓN
------------------------------------------------------------------------
RNF-11.1 [ALTA]   La interfaz debe estar completamente en español
         latinoamericano.
RNF-11.2 [MEDIA]  Los formatos de fecha deben ser DD/MM/YYYY o adaptados a la
         convención local.
RNF-11.3 [MEDIA]  La validación de teléfono debe reconocer y manejar el
         prefijo de país de Nicaragua (+505).
RNF-11.4 [MEDIA]  Los valores monetarios deben mostrarse con el símbolo de
         moneda local y separadores de miles apropiados.

------------------------------------------------------------------------
RNF-12: TRAZABILIDAD Y AUDITORÍA
------------------------------------------------------------------------
RNF-12.1 [ALTA]   El sistema debe mantener un registro inmutable de todos los
         cambios realizados a los productos mediante triggers de base de datos
         (PostgreSQL).
RNF-12.2 [ALTA]   Cada movimiento de inventario debe tener una referencia que
         identifique el origen del cambio (orden de compra, orden de venta,
         ajuste manual).
RNF-12.3 [MEDIA]  Los registros de auditoría deben almacenar snapshots
         completos en formato JSON del estado anterior y posterior del registro
         modificado.
RNF-12.4 [BAJA]   El sistema debe registrar opcionalmente la dirección IP del
         usuario en los logs de auditoría.


================================================================================
4. RESTRICCIONES TÉCNICAS
================================================================================

RT-01  [ALTA]   Se requiere PostgreSQL 16+ en producción. No se soporta SQLite
       en producción debido al uso de JSONB, triggers y funciones específicas
       de PostgreSQL.

RT-02  [ALTA]   El almacenamiento de imágenes requiere acceso a Cloudflare R2
       o un servicio compatible con la API de Amazon S3 (bucket_name,
       access_key, secret_key, endpoint_url).

RT-03  [ALTA]   El backend requiere Python 3.12 o superior.

RT-04  [ALTA]   El frontend requiere Node.js 18+ para construcción con Vite 7.

RT-05  [ALTA]   El despliegue en producción requiere HTTPS para garantizar la
       seguridad de los datos en tránsito.

RT-06  [ALTA]   Las migraciones de base de datos deben ejecutarse en orden
       estricto para mantener la integridad referencial del esquema.


================================================================================
5. ENTIDADES Y RELACIONES PRINCIPALES
================================================================================

  Producto         --> Categoria (N:1)
  Producto         --> Marca (N:1)
  Producto         --> Proveedor (N:1, opcional)
  Proveedor        --> OrdenCompra (1:N)
  OrdenCompra      --> DetalleOrdenCompra (1:N) --> Producto (N:1)
  Cliente          --> OrdenVenta (1:N)
  OrdenVenta       --> DetalleOrdenVenta (1:N) --> Producto (N:1)
  Cliente          --> Moto (1:N)
  Moto             --> ServicioMoto (1:N)
  ServicioMoto     --> BitacoraServicio (1:1)
  Producto         --> MovimientoInventario (1:N)
  Producto         --> AuditoriaProducto (1:N) [via trigger]

7. HISTORIAS DE USUARIO DE ALTO NIVEL
================================================================================

HU-01  Como administrador, quiero ver el estado del inventario en tiempo real
       para tomar decisiones de reabastecimiento oportunas.

HU-02  Como vendedor, quiero registrar una venta rápidamente seleccionando
       cliente y productos, para que el stock se actualice automáticamente.

HU-03  Como comprador, quiero crear una orden de compra a un proveedor y
       registrar su recepción para actualizar el inventario sin errores manuales.

HU-04  Como técnico, quiero documentar cada etapa del servicio a una moto con
       fotos y notas, para mantener un registro profesional del trabajo realizado.

HU-05  Como gerente, quiero generar reportes de ventas por período en Excel o
       PDF para presentar resultados a la dirección.

HU-06  Como auditor, quiero ver el historial completo de cambios en el inventario
       con usuario y fecha para garantizar la trazabilidad de los datos.

HU-07  Como usuario, quiero buscar cualquier producto, cliente o proveedor
       desde cualquier pantalla con un atajo de teclado para trabajar más rápido.
