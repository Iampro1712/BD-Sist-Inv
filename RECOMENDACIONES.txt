CAPÍTULO V: RECOMENDACIONES
═══════════════════════════════════════════════════════════════════════════════

  Con base en los hallazgos del proceso de desarrollo del sistema Inventrix,
  los resultados obtenidos en cada sprint de implementación y los estudios de
  factibilidad técnica y económica realizados, se formulan las siguientes
  recomendaciones dirigidas a tres audiencias: el equipo técnico que continúe
  el desarrollo, los futuros clientes o adoptantes del sistema, y los
  investigadores o desarrolladores que retomen o extiendan este trabajo.

  Las recomendaciones se organizan por áreas temáticas de acuerdo con las
  dimensiones analizadas a lo largo del presente estudio.


═══════════════════════════════════════════════════════════════════════════════
5.1 RECOMENDACIONES TÉCNICAS PARA EL EQUIPO DE DESARROLLO
═══════════════════════════════════════════════════════════════════════════════

  5.1.1 Implementación del Sistema de Autenticación y Control de Acceso

  Se recomienda como prioridad inmediata para la versión 2.0 del sistema la
  implementación de un módulo de autenticación de usuarios basado en JSON Web
  Tokens (JWT) mediante la biblioteca djangorestframework-simplejwt. En el
  estado actual del sistema (v1.0), todos los endpoints de la API REST son
  accesibles sin autenticación previa, lo que representa el riesgo de seguridad
  más crítico del sistema antes de su despliegue en un entorno de producción
  real con datos sensibles del negocio si lo llegara a usar mas de 1 persona.

  Junto con la autenticación, se recomienda implementar un sistema de roles y
  permisos que distinga al menos tres niveles de acceso: administrador (acceso
  total), supervisor (acceso de lectura y registro sin eliminación) y empleado
  (acceso restringido a módulos operativos). Esta funcionalidad está contemplada
  en el roadmap del proyecto para la versión 2.1 (Q2 2026) y debe considerarse
  bloqueante para el despliegue en producción.

  5.1.2 Extensión de la Cobertura de Pruebas Automatizadas

  Se recomienda desarrollar una suite de pruebas automatizadas que cubra al
  menos los flujos críticos del sistema: creación y recepción de órdenes de
  compra, registro de ventas con validación de stock, ajuste manual de
  inventario y escritura en los triggers de auditoría de PostgreSQL. La ausencia
  de pruebas automatizadas en el ciclo de desarrollo actual implica que los
  cambios futuros podrían introducir regresiones no detectadas hasta producción.

  Se sugiere adoptar pytest-django para pruebas del backend y Playwright o
  Vitest con React Testing Library para pruebas de integración del frontend.
  El objetivo inicial debe ser alcanzar una cobertura del 70% en la capa de
  serializers y modelos del backend, ya que estos concentran la lógica de
  negocio crítica del sistema.

  5.1.3 Implementación de Monitoreo y Alertas en Producción

  Se recomienda integrar una solución de monitoreo de errores en tiempo real,
  preferentemente Sentry (en su plan gratuito para proyectos individuales),
  tanto en el backend de Django como en el frontend de React. Esta herramienta
  permite identificar excepciones no controladas en producción sin necesidad
  de acceder manualmente a los logs del servidor, reduciendo significativamente
  el tiempo de detección y resolución de fallos.

  Complementariamente, se sugiere configurar alertas de salud del sistema
  mediante un servicio de monitoreo de uptime como UptimeRobot (plan gratuito),
  que notifique al administrador del sistema si el servidor backend deja de
  responder.

  5.1.4 Optimización de Consultas de Base de Datos para Módulos de Reporte

  Las consultas de los módulos de reportes (RF-13) involucran agregaciones
  sobre múltiples tablas relacionadas con filtros de rango de fechas. Se
  recomienda revisar el plan de ejecución de estas consultas con el comando
  EXPLAIN ANALYZE de PostgreSQL y agregar índices compuestos en los campos
  fecha y producto_id de las tablas de órdenes de venta, órdenes de compra
  y movimientos de inventario. Esta optimización cobrará mayor importancia
  cuando el volumen de datos históricos supere los 10,000 registros.

  5.1.5 Versionamiento de la API REST

  Se recomienda introducir versionamiento en los endpoints de la API (por
  ejemplo, /api/v1/ como prefijo), anticipando que las versiones futuras del
  sistema (2.0, 2.1) podrían modificar los contratos de respuesta de algunos
  endpoints. El versionamiento permite mantener compatibilidad con integraciones
  externas existentes mientras se introduce la nueva versión de la API de manera
  gradual.

  5.1.6 Gestión de Migraciones de Base de Datos en Producción

  Se recomienda documentar y estandarizar el procedimiento de aplicación de
  migraciones de Django en entornos de producción, incluyendo la creación de
  un respaldo de la base de datos previo a cualquier migración y la verificación
  del estado de las migraciones post-aplicación. Este proceso debe incluirse
  en el runbook operacional del sistema y ejecutarse siempre dentro de una
  ventana de mantenimiento acordada con el cliente.

5.2 RECOMENDACIONES FUNCIONALES Y DE PRODUCTO
═══════════════════════════════════════════════════════════════════════════════

  5.2.1 Incorporación del Módulo de Facturación Electrónica

  Se recomienda evaluar en versiones futuras la integración con el sistema de
  facturación electrónica vigente en Nicaragua (conforme a las disposiciones
  de la Dirección General de Ingresos, DGI), de modo que el sistema pueda
  emitir facturas fiscales desde el módulo de órdenes de venta. Esta
  funcionalidad elevaría sustancialmente el valor comercial del sistema para
  negocios formalmente constituidos, diferenciándolo de las alternativas de
  mercado revisadas en el estudio de factibilidad económica.

  5.2.2 Desarrollo de Aplicación Móvil Nativa

  Dado que el sistema fue concebido con una arquitectura de API REST desacoplada,
  se recomienda desarrollar una aplicación móvil nativa (React Native o Flutter)
  que consuma los mismos endpoints del backend ya existente. Esta aplicación
  podría priorizar los flujos de uso más frecuentes en dispositivos móviles:
  consulta de stock, registro rápido de ventas y captura fotográfica para la
  bitácora de servicios. El roadmap del proyecto contempla esta extensión para
  la versión 2.1 (Q2 2026).

  5.2.3 Módulo de Notificaciones de Bajo Stock Proactivas

  Se recomienda implementar un sistema de notificaciones proactivas que informe
  al administrador del negocio cuando el stock de uno o más productos caiga por
  debajo del umbral mínimo definido (RF-01.3). La implementación puede realizarse
  mediante correo electrónico con Django Signals y Celery (cola de tareas
  asíncronas), o mediante notificaciones push en el navegador usando la Web
  Notifications API. Esta mejora reduce la dependencia del usuario de revisar
  activamente el dashboard para detectar alertas de inventario.

  5.2.4 Exportación de la Bitácora de Servicios en PDF

  Se recomienda extender el módulo de exportación (RNF-10) para generar un
  documento PDF de la bitácora completa de un servicio, incluyendo las fotografías
  cargadas en Cloudflare R2 embebidas en el documento. Este reporte puede
  entregarse al cliente del taller como comprobante del trabajo realizado, lo
  que representa una mejora directa en la percepción de profesionalismo del
  negocio y reduce conflictos post-servicio.

  5.2.5 Soporte Multi-Sucursal

  Para negocios que operen con más de una ubicación física, se recomienda diseñar
  una extensión de la arquitectura de datos que soporte el concepto de sucursal
  o sede. Cada inventario, proveedor y registro de ventas quedaría asociado a
  una sucursal específica, con la posibilidad de consolidar reportes a nivel de
  empresa. Esta funcionalidad, contemplada en el roadmap v2.1, requeriría la
  revisión del modelo de datos existente para incorporar la dimensión de sucursal
  en las entidades principales.

5.3 RECOMENDACIONES PARA LA ADOPCIÓN DEL SISTEMA POR PARTE DEL CLIENTE
═══════════════════════════════════════════════════════════════════════════════

  5.3.1 Plan de Migración de Datos desde Registros Actuales

  Se recomienda que el negocio cliente planifique con anticipación la migración
  de su catálogo de productos existente al sistema Inventrix antes de la fecha
  de puesta en marcha. Esta migración puede realizarse mediante la importación
  masiva desde una hoja de cálculo (CSV) a través de un script de carga inicial,
  o mediante el ingreso manual asistido para catálogos pequeños. La continuidad
  operativa durante la transición depende en gran medida de la calidad y
  completitud de los datos de origen.

  5.3.2 Capacitación del Personal Operativo

  Se recomienda destinar entre cuatro y ocho horas de capacitación práctica al
  equipo de empleados que utilizará el sistema diariamente, con énfasis en los
  módulos de mayor uso: registro de ventas, consulta de stock y creación de
  órdenes de compra. La capacitación debe realizarse sobre el entorno de
  producción real, con datos de prueba que simulen la operación normal del
  negocio, y ser impartida por el equipo de desarrollo como parte de los
  entregables del contrato (Hito 5).

  5.3.3 Definición de un Proceso de Respaldo Periódico

  Se recomienda que el cliente establezca un procedimiento claro de verificación
  periódica de los respaldos automáticos de la base de datos. Aunque el equipo
  de desarrollo configure los backups automáticos diarios, la responsabilidad
  de verificar que los respaldos se ejecuten correctamente y de probar una
  restauración al menos una vez por mes recae en el administrador designado
  del sistema por parte del cliente.

  5.3.4 Designación de un Administrador Técnico Interno

  Se recomienda que el negocio designe a un empleado con conocimientos básicos
  de informática como administrador interno del sistema, responsable de: crear
  y gestionar las cuentas de usuario (cuando se implemente autenticación),
  coordinar con el equipo de soporte técnico ante fallas, y comunicar las
  necesidades de ajuste o mejora del sistema. Esto reduce la dependencia
  completa del proveedor de desarrollo para tareas administrativas rutinarias.


═══════════════════════════════════════════════════════════════════════════════
5.4 RECOMENDACIONES PARA TRABAJOS FUTUROS E INVESTIGACIÓN
═══════════════════════════════════════════════════════════════════════════════

  5.4.1 Evaluación de Rendimiento bajo Carga Real

  Se recomienda realizar pruebas de carga (load testing) con herramientas como
  Locust o k6 antes del despliegue en producción con datos reales, simulando
  el uso simultáneo de al menos diez usuarios realizando operaciones de escritura.
  Estas pruebas permitirán identificar cuellos de botella en los serializers del
  backend o en las consultas de la base de datos antes de que impacten la
  operación real del negocio.

  5.4.2 Investigación sobre Inteligencia Artificial Aplicada al Inventario

  Se recomienda explorar, como trabajo de investigación futuro, la viabilidad
  de incorporar modelos de predicción de demanda basados en el historial de
  ventas almacenado en el sistema. La arquitectura de API REST existente
  facilitaría la integración de un microservicio de Python con bibliotecas
  de machine learning (scikit-learn, Prophet) que consuma los datos de
  movimientos de inventario para generar sugerencias de reabastecimiento.
  Esta línea de investigación es especialmente relevante en el contexto de
  talleres de motos con demanda estacional.

  5.4.3 Estudio de Usabilidad con Usuarios Reales

  Se recomienda llevar a cabo un estudio de usabilidad formal con usuarios
  representativos del perfil objetivo (operadores de talleres de motos o
  negocios de venta minorista en Nicaragua), utilizando metodologías como
  pruebas de usuario moderadas o cuestionarios SUS (System Usability Scale).
  Los resultados orientarían mejoras en la interfaz de usuario que actualmente
  fueron diseñadas con base en criterios técnicos y de funcionalidad, pero sin
  validación empírica con usuarios finales del contexto cultural específico.

  5.4.4 Análisis de Seguridad Formal (Pentesting)

  Se recomienda someter el sistema a un análisis de seguridad formal mediante
  pruebas de penetración (pentesting) antes de su despliegue en producción
  con datos reales del negocio. Este análisis debe incluir, como mínimo:
  verificación de inyección SQL en los endpoints de la API, pruebas de
  escalación de privilegios cuando se implemente autenticación, y análisis
  de exposición de información sensible en las respuestas de la API. Este
  paso es especialmente importante dado que el sistema maneja datos
  financieros y operativos del negocio.

  5.4.5 Adaptación del Sistema para Otros Segmentos de PyMEs

  Se recomienda estudiar la posibilidad de adaptar el sistema Inventrix para
  otros segmentos de pequeñas y medianas empresas más allá de los talleres
  de motos, tales como ferreterías, pulperías o pequeños almacenes de
  distribución. La arquitectura modular del sistema facilita la incorporación
  de nuevos módulos especializados sin refactorización mayor de los componentes
  existentes, lo que representa una oportunidad de escalamiento comercial
  del producto en el mercado nicaragüense y centroamericano.
